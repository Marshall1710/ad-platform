# Спецификация: локальный каркас проекта

**Feature Branch**: `main`
**Created**: 2026-11-06
**Status**: Согласовано
**Input**: Подготовить локально запускаемые кабинет, тестовый Аукцион, DSP и две PostgreSQL с npm-скриптами запуска, сборки и тестов.

## Согласованный объём и границы решений

Результат: все три приложения и обе базы собираются и запускаются локально через Docker Compose; из корня проекта работают команды запуска, сборки и проверки. Подготовка выполняется в main, после проверки — коммит и push. Пользовательские функции кабинета, выбор ставки, события аукциона и статистика относятся к следующим спекам. Исходное задание остаётся вне репозитория, README не ссылается на внешние локальные файлы.

## User Scenarios & Testing

### User Story 1 — Поднять локальный стенд (Priority: P1)

Разработчик выполняет одну команду в корне репозитория и получает доступные кабинет, Аукцион и DSP; обе базы показывают готовность.

**Independent Test**: На чистом локальном окружении с Docker выполнить команду запуска, проверить состояние пяти контейнеров и HTTP-ответы приложений.

**Acceptance Scenarios**:

1. **Given** установлен Docker и получен репозиторий, **When** разработчик выполняет `npm run up`, **Then** три приложения доступны по документированным адресам и обе PostgreSQL готовы.
2. **Given** стенд запущен, **When** разработчик выполняет `npm run down`, **Then** пять контейнеров остановлены без удаления данных БД.

### User Story 2 — Собирать и проверять каркас (Priority: P2)

Разработчик может отдельно собрать приложения и запустить воспроизводимую проверку стенда через npm-скрипты.

**Independent Test**: Выполнить `npm run build`, затем `npm test` на запущенном стенде.

**Acceptance Scenarios**:

1. **Given** зависимости установлены, **When** разработчик выполняет `npm run build`, **Then** образы кабинета, Аукциона и DSP собираются без ошибки.
2. **Given** стенд запущен, **When** разработчик выполняет `npm test`, **Then** проверка подтверждает доступность трёх приложений и готовность двух БД либо явно сообщает о неисправном компоненте.

### Edge Cases

- Если Docker недоступен или один из портов занят, команда должна завершиться ошибкой, а инструкция в README должна помочь обнаружить причину.
- Проверка не должна показывать успех, если хотя бы одно приложение или одна БД недоступны.

## Requirements

### Functional Requirements

- **FR-001**: Репозиторий MUST содержать отдельные каталоги apps/cabinet, apps/auction и apps/dsp.
- **FR-002**: Кабинет и Аукцион MUST быть отдельными Next.js-приложениями на TypeScript; DSP MUST быть отдельным Go-приложением.
- **FR-003**: Docker Compose MUST запускать три приложения и две независимые PostgreSQL с разными постоянными томами.
- **FR-004**: Корневые npm-скрипты MUST запускать, останавливать, собирать и проверять стенд.
- **FR-005**: Проверка MUST различать отказ каждого из пяти компонентов.
- **FR-006**: README MUST содержать команды, адреса, требования к окружению и фактические границы каркаса.

## Success Criteria

### Measurable Outcomes

- **SC-001**: После `npm run up` работают 5 контейнеров; оба интерфейса и DSP отвечают по документированным адресам.
- **SC-002**: `npm run build` завершается успешно для всех 3 приложений.
- **SC-003**: `npm test` подтверждает доступность 3 приложений и готовность 2 баз, завершаясь ненулевым кодом при отказе любого компонента.
- **SC-004**: Команды и результаты реального локального прогона записаны в verification.md.

## Assumptions

- На этом этапе приложения показывают стартовые страницы или служебный ответ; бизнес-сценарии будут добавлены по следующим спецификациям.
- Контейнеры приложений обмениваются данными по внутренней сети Docker Compose.
- Локальная установка Go используется для разработки и тестов, работающий стенд запускается через Docker.
