# Эпики проекта «Тестовый аукцион»

Статус: согласованные границы первой версии. Подробный итог груминга каждой функции фиксируется в её Spec Kit spec.md; в docs/features/ поддерживается документация действующей логики функции, без истории изменений.

## Что строим

| Компонент | Ответственность | Данные |
| --- | --- | --- |
| Кабинет рекламодателя | Регистрация и вход, управление кампаниями, креативами и ставками, просмотр статистики с учётом роли | Собственная PostgreSQL: пользователи, кампании, креативы, настройки |
| DSP | Получение актуальных настроек кампаний, ответы на bid request, обработка побед, показов и кликов, расчёт расхода | Собственная PostgreSQL: данные для торгов, события, расход и статистика |
| Тестовый Аукцион | Настройка тестового запроса, отправка его в DSP, определение победы по порогу и отправка тестовых событий | Собственной БД нет |

Кабинет и DSP не читают таблицы друг друга напрямую. Кабинет передаёт изменения кампаний в DSP и получает статистику через внутренний API DSP. Аукцион имитирует внешнюю биржу для проверки нашего DSP; конкуренцию нескольких DSP и полноценную биржу не строим.

Для локального запуска используем Docker Compose: три приложения и два отдельных контейнера PostgreSQL, по одному для кабинета и DSP. У Аукциона собственной БД нет.

Стек приложений: кабинет и тестовый Аукцион — два отдельных Next.js-приложения на TypeScript; DSP — отдельный сервис на Go. Оба Next.js-приложения включают интерфейс и свой серверный HTTP API.

## Сквозной сценарий

| Шаг | Наблюдаемый результат |
| --- | --- |
| 1. Рекламодатель входит в кабинет | Может создавать и менять только свои кампании; администратор видит всех пользователей и их кампании. |
| 2. Рекламодатель готовит кампанию | Указывает модель и сумму ставки, три таргета и один баннерный креатив 300×250 с изображением и обязательной ссылкой перехода. |
| 3. Рекламодатель включает кампанию | Кабинет сохраняет статус и передаёт актуальные настройки в DSP. Само включение bid request не создаёт. |
| 4. Пользователь вручную запускает запрос в Аукционе | DSP выбирает подходящую активную кампанию с максимальной сравнимой ставкой либо отвечает HTTP 204. |
| 5. Аукцион проверяет порог | При достаточной ставке сообщает DSP о победе и автоматически отправляет один показ; при 204 или ставке ниже порога событий победы и показа нет. |
| 6. Аукцион имитирует клик, если это включено | После показа инициирует один клик через DSP; DSP учитывает его и перенаправляет на ссылку креатива. |
| 7. Рекламодатель смотрит статистику | Видит участия, победы, показы, клики и расход только по своим кампаниям; администратор видит данные всех. |

## Эпики

| № | Эпик | Результат и граница готовности |
| --- | --- | --- |
| 1 | Кабинет и доступ | Рекламодатель самостоятельно регистрируется и входит. Роли advertiser и admin проверяются на сервере: чужие кампании и статистика рекламодателю недоступны, администратору доступны данные всех. |
| 2 | Кампании и креативы | В кабинете создают, меняют, включают и выключают кампанию баннерного формата 300×250. У кампании не более одного креатива; для включения он обязателен. Креатив содержит название, изображение и обязательную ссылку перехода. Таргеты кампании: country, adult и device. Изменения передаются в DSP. |
| 3 | Настройка ставок | Для кампании выбирают CPC или CPM и задают сумму ставки. Кабинет проверяет и показывает выбранную модель и сумму. DSP приводит ставки к сравнимому значению для внутреннего выбора кампании. Предварительно согласован eCPM с фиксированным ожидаемым CTR 1%; точное правило закрепляется при проработке эпика. |
| 4 | DSP и внутренний отбор | DSP получает данные кампаний из кабинета, принимает bid request, применяет формат и все три таргета. Из подходящих активных кампаний с креативом выбирает максимальную сравнимую ставку; если кандидатов нет, отвечает 204. Возвращает ставку, её идентификатор и единственный креатив кампании. Принимает уведомления о победе и показе, учитывает клик и перенаправляет на ссылку креатива. |
| 5 | Тестовый Аукцион | Можно задать country, adult, device, CPM-порог и переключатель «Имитировать клик», вручную отправить запрос и увидеть входные данные, ответ и результат. Ставка не ниже порога побеждает: Аукцион отдельно сообщает DSP о победе, затем отправляет один показ и, при включённом переключателе, один клик. При проигрыше и 204 этих событий нет. Новый показ или клик требует нового запроса и новой победы. |
| 6 | Статистика и расход | DSP считает участие кампании при ответе ставкой, а победу, показ и клик — по соответствующим событиям. 204 не добавляет участия кампании. Расход CPM возникает при показе в размере ставки за тысячу показов, делённой на 1000; расход CPC — при клике в размере ставки за клик. Повтор события не удваивает счётчики и расход. Кабинет показывает статистику по кампаниям и периоду с проверкой роли. |
| 7 | Полнота проверки | Для согласованных требований есть проверяемые критерии и тесты. Проверяются роли и изоляция данных, ограничения кампании и креатива, все таргеты, CPC/CPM, выбор максимальной ставки, 204, порог, победа, автоматический показ, переключатель клика, редирект, расход и повторная доставка. Интеграционные и сквозные проверки покрывают обмен кабинета, DSP и Аукциона. Эпик выполняется на протяжении разработки остальных эпиков. |

Автоматическая генерация bid request скриптом возможна позднее через тот же сценарий Аукциона; в первую версию она не входит.

## Инварианты первой версии

- Ссылка перехода принадлежит креативу. Отдельной ссылки у кампании нет.
- Кампания без креатива не может быть включена; у одной кампании не бывает нескольких креативов.
- Во всех трёх компонентах используются одинаковые поля таргетинга: country, adult (булево значение) и device.
- Участие кампании возникает при ответе DSP ставкой, независимо от того, победила она или нет. Ответ 204 не создаёт участия кампании.
- Победа и показ — разные события, хотя тестовый Аукцион отправляет их подряд.
- Один выигравший тестовый запрос создаёт не более одного показа и одного клика. Повторная доставка события не создаёт повторный расход.

## Согласованный подход к тестам

| Слой | Инструменты | Что подтверждаем |
| --- | --- | --- |
| Кабинет и Аукцион | Vitest; React Testing Library для интерактивных компонентов | Бизнес-правила, формы и реакции интерфейса |
| DSP | Go testing и httptest | Отбор кампании, HTTP-ответы, события, расчёт расхода и редирект |
| Интеграция с БД | Testcontainers для Node.js и Go с настоящими PostgreSQL | Миграции, сохранение данных, транзакции и отсутствие повторного учёта |
| Сервисы вместе | Проверки HTTP-контрактов и Playwright поверх Docker Compose | Полный сценарий от регистрации до статистики и изоляция ролей |

К каждому критерию приёмки в spec.md нужен проверяющий его тест. Для асинхронных серверных компонентов Next.js используем сквозные проверки. Процент покрытия анализируем как сигнал о пробелах, без произвольной цели 100%. Агент записывает реально выполненные проверки в verification.md.
## Детали для груминга функций

Эти вопросы не меняют утверждённые границы эпиков и не мешают начать работу. Решения по ним фиксируются в spec.md соответствующей функции до реализации затронутого поведения:

- Контракт передачи настроек из кабинета в DSP, сбои и повторы, момент доступности изменений для торгов.
- Идентификаторы запросов, ставок и событий, обработка повторных и пришедших не по порядку уведомлений.
- Точная формула сравнения CPC и CPM, единицы и точность денежных сумм, правило равенства ставок.
- Допустимые значения и смысл country, adult и device на уровне API.
- Отображение ошибок DSP в Аукционе.
- Периоды и разрезы статистики, создание первого администратора, защита внутреннего API.
- Конкретные библиотеки, версии и инструменты разработки и тестирования; языки и основные фреймворки уже утверждены.
