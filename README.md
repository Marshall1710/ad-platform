# Тестовый аукцион

Проект тестового рекламного кабинета, DSP и Аукциона для проверки полного пути от настройки кампании до статистики. Сейчас готов локально запускаемый каркас: два Next.js-приложения, Go-сервис и две отдельные PostgreSQL. Продуктовая логика будет добавлена по следующим спецификациям.

## Состав проекта

| Приложение | Назначение | Стек и данные |
| --- | --- | --- |
| Кабинет рекламодателя | Пользователи, кампании, креативы, ставки и просмотр статистики | Next.js + TypeScript, собственная PostgreSQL |
| DSP | Отбор кампании на bid request, события победы, показа и клика, расход и статистика | Go, собственная PostgreSQL |
| Тестовый Аукцион | Ручная отправка bid request, проверка порога и имитация событий | Next.js + TypeScript, без БД |

Для локального запуска согласован Docker Compose: три приложения и два отдельных контейнера PostgreSQL. Кабинет и DSP обмениваются данными через API и не читают таблицы друг друга.

## Сквозной сценарий

| Шаг | Наблюдаемый результат |
| --- | --- |
| 1. Рекламодатель входит в кабинет | Может создавать и менять только свои кампании; администратор видит всех пользователей и их кампании. |
| 2. Рекламодатель готовит кампанию | Указывает модель и сумму ставки, три таргета и один баннерный креатив 300×250 с изображением и обязательной ссылкой перехода. |
| 3. Рекламодатель включает кампанию | Кабинет сохраняет статус и передаёт актуальные настройки в DSP. Само включение bid request не создаёт. |
| 4. Пользователь вручную запускает запрос в Аукционе | DSP выбирает подходящую активную кампанию с максимальной сравнимой ставкой либо отвечает HTTP 204. |
| 5. Аукцион проверяет порог | При достаточной ставке сообщает DSP о победе и автоматически отправляет один показ; при 204 или ставке ниже порога событий победы и показа нет. |
| 6. Аукцион имитирует клик, если это включено | После показа инициирует один клик через DSP; DSP учитывает его и перенаправляет на ссылку креатива. |
| 7. Рекламодатель смотрит статистику | Видит участия, победы, показы, клики и расход только по своим кампаниям; администратор видит данные всех. |

## Работа с Git

- Для каждого эпика используется одна ветка `epic/<название-эпика>` без номера, например `epic/cabinet-access`.
- Каждая согласованная спецификация хранится в отдельной папке `specs/<имя>`. Сообщение коммита начинается с `feat:` для новой функции, `fix:` для исправления бага, `refactor:` для улучшения существующего кода или `chore:` для прочей работы. Для коммита по спецификации после префикса указываем точное имя её папки, например `feat: 001-registration`; отдельную нумерацию не добавляем. Для подготовительной работы без спеки указываем краткое название работы.
- Контрольные точки между спецификацией, планом и реализацией определяем для конкретной задачи; общий порядок ещё не утверждён.
- Перед завершением эпика проверяем всю ветку, запускаем необходимые тесты и при необходимости проводим рефакторинг.
- Pull request создаёт пользователь вручную; агент не создаёт PR.
- Подготовка каркаса выполняется в main по отдельной спецификации и коммитится как `chore: 001-project-bootstrap`.

## Локальный запуск

Нужны Docker Desktop с запущенным Docker daemon, Node.js 22 и npm. Go 1.27 нужен для локального запуска Go-тестов; сам DSP собирается в Docker.

| Компонент | Адрес |
| --- | --- |
| Кабинет рекламодателя | http://localhost:3000/ |
| Тестовый Аукцион | http://localhost:3001/ |
| DSP, проверка доступности | http://localhost:8080/health |
| PostgreSQL кабинета и DSP | Доступны только внутри сети Docker Compose |

Пароли PostgreSQL в `compose.yaml` предназначены только для локального стенда; базы не публикуют порты на хосте.

Из корня репозитория:

```powershell
npm ci
npx playwright install chromium
npm run build
npm run up
npm test
```

`npm run up` собирает образы, оставляет пять контейнеров работающими и ждёт до 30 секунд ответа трёх приложений. После готовности команда печатает три кликабельные локальные ссылки. Если приложение недоступно, она показывает его имя и адрес и завершается ошибкой; контейнеры остаются запущенными.

`npm test` требует запущенного стенда: проверяет готовность обеих PostgreSQL и открывает интерфейсы кабинета и Аукциона в Chromium; DSP проверяется по HTTP. Команда завершается с ошибкой, если один из компонентов недоступен.

`npm run down` останавливает стенд и сохраняет тома БД. `npm run typecheck` проверяет TypeScript обоих Next-приложений; `npm run test:go` запускает Go-тесты локально. После установки Go может понадобиться новое окно терминала для обновления PATH. Проверки вывода ссылок можно запустить отдельно командой `npm run test:startup`.

Сейчас это запускаемый каркас: страницы и служебный ответ DSP подтверждают доступность приложений. Регистрация, кампании, торги и статистика будут реализовываться по отдельным спецификациям.

Для просмотра логов используйте `docker compose logs -f cabinet` (или `auction`, `dsp`). В режиме `up` приложения работают из готовых Docker-образов: после изменения исходников повторите `npm run up` и обновите страницу в браузере.

## Разработка интерфейсов

Для правок интерфейса используйте Next Dev: `npm run dev:cabinet` для кабинета
или `npm run dev:auction` для Аукциона. Каждая команда поднимает DSP и две базы
в Docker, останавливает Docker-контейнер соответствующего фронтенда и запускает
Next локально на прежнем адресе. Если нужны оба интерфейса, запускайте команды
в двух терминалах. После сохранения исходника Next обновляет страницу без сборки
Docker-образа.

Режим разработки работает, пока его терминал открыт. Перед возвратом к полному
Docker-стенду остановите dev-процессы и выполните `npm run up`. Базы пока доступны
только в сети Docker; когда серверному коду Next понадобится прямой доступ к БД,
для локального dev-режима потребуется отдельная настройка соединения.
