# Тестовый аукцион

Проект тестового рекламного кабинета, DSP и Аукциона для проверки полного пути от настройки кампании до статистики. Сейчас запущены два Next.js-приложения, Go-сервис и две отдельные PostgreSQL. В кабинете реализованы регистрация рекламодателя, общий вход и выход, ручное создание администратора и защищённая заглушка. Кампании, торги и статистика будут добавлены по следующим спецификациям.

## Состав проекта

| Приложение | Назначение | Стек и данные |
| --- | --- | --- |
| Кабинет рекламодателя | Пользователи, кампании, креативы, ставки и просмотр статистики | Next.js + TypeScript, собственная PostgreSQL |
| DSP | Отбор кампании на bid request, события победы, показа и клика, расход и статистика | Go, собственная PostgreSQL |
| Тестовый Аукцион | Ручная отправка bid request, проверка порога и имитация событий | Next.js + TypeScript, без БД |

Для локального запуска используется Docker Compose: три приложения и два отдельных контейнера PostgreSQL. По целевой архитектуре кабинет и DSP будут обмениваться данными через API без прямого чтения таблиц друг друга.

## Планируемый сквозной сценарий

Ниже описан целевой путь проекта. Сейчас реализован только доступ к кабинету; шаги с кампаниями, DSP, Аукционом и статистикой ещё не реализованы.

| Шаг | Наблюдаемый результат |
| --- | --- |
| 1. Рекламодатель входит в кабинет | Может создавать, менять, включать, выключать и удалять свои кампании. Администратор видит email и роль пользователей и может выполнять те же действия с кампаниями выбранного рекламодателя. |
| 2. Рекламодатель готовит кампанию | Может сохранить кампанию без настроек. Для включения задаёт категорию трафика, модель и сумму ставки и добавляет креатив 300×250. Таргеты страны и устройства необязательны. |
| 3. Рекламодатель включает кампанию | Кабинет сохраняет статус и сразу подтверждает включение. DSP получает кампанию из API кабинета при следующей успешной синхронизации. Само включение bid request не создаёт. |
| 4. Пользователь вручную запускает запрос в Аукционе | DSP применяет правила отбора по формату, стране, устройству и категории трафика. Она возвращает максимальную сравнимую ставку внутри выбранной категории либо отвечает HTTP 204. |
| 5. Аукцион проверяет порог | При достаточной ставке сообщает DSP о победе и автоматически отправляет один показ; при 204 или ставке ниже порога событий победы и показа нет. |
| 6. Аукцион имитирует клик, если это включено | После показа инициирует один клик через DSP; DSP учитывает его и перенаправляет на ссылку креатива. |
| 7. Рекламодатель смотрит статистику | Видит участия, победы, показы, клики и расход по своим кампаниям. Администратор открывает отчёт выбранного рекламодателя. При сбое DSP кабинет предоставляет сохранённую статистику с временем обновления, если данные есть. |

## Работа с Git

- Для каждого эпика используется одна ветка `epic/<название-эпика>` без номера, например `epic/cabinet-access`.
- Каждая согласованная спецификация хранится в отдельной папке `specs/<имя>`. Сообщение коммита начинается с `feat:` для новой функции, `fix:` для исправления бага, `refactor:` для улучшения существующего кода или `chore:` для прочей работы. Для коммита по спецификации после префикса указываем точное имя её папки, например `feat: 001-registration`; отдельную нумерацию не добавляем. Для подготовительной работы без спеки указываем краткое название работы.
- Контрольные точки между спецификацией, планом и реализацией определяем для конкретной задачи; общий порядок ещё не утверждён.
- Перед завершением эпика проверяем всю ветку, запускаем необходимые тесты и при необходимости проводим рефакторинг.
- Pull request создаёт пользователь вручную; агент не создаёт PR.
- Подготовка каркаса выполняется в main по отдельной спецификации и коммитится как `chore: 001-project-bootstrap`.

## Локальный запуск

Нужны Docker Desktop с запущенным Docker daemon, Node.js 22 и npm. Go 1.27 нужен для локального запуска Go-тестов; сам DSP собирается в Docker.

| Компонент | Адрес |
| --- | --- |
| Кабинет рекламодателя | http://127.0.0.1:3000/ |
| Тестовый Аукцион | http://127.0.0.1:3001/ |
| DSP, проверка доступности | http://127.0.0.1:8080/health |
| PostgreSQL кабинета | 127.0.0.1:5433 только для локального Next Dev; также доступна в сети Compose |
| PostgreSQL DSP | Только в сети Docker Compose |

Адрес и порты в таблице — значения по умолчанию. Для своей машины скопируйте `.env.example`
в `.env` и измените `LOCAL_HOST`, `CABINET_PORT`, `AUCTION_PORT`, `DSP_PORT`, `CABINET_DB_PORT`. Команда `npm run setup:local` создаёт `.env` и случайный `AUTH_SECRET`, если их ещё нет; `npm run up` и `npm run dev:cabinet` вызывают её автоматически.
`.env` не попадает в Git; один набор значений используют Docker Compose, Next Dev,
ссылки после запуска и smoke-тесты. `LOCAL_HOST` — локальный IP-адрес,
на котором слушают приложения, например `127.0.0.1`.

Пароли PostgreSQL в `compose.yaml` предназначены только для локального стенда. База кабинета публикуется исключительно на 127.0.0.1 для локального Next Dev; база DSP не публикуется.

Из корня репозитория:

```powershell
npm ci
npx playwright install chromium
npm run build
npm run up
npm test
```

`npm run up` собирает образы, оставляет пять контейнеров работающими и ждёт до 30 секунд ответа трёх приложений. Docker Compose выводит прогресс обычными строками. После готовности команда печатает три кликабельные локальные ссылки в терминале запуска, в том числе в выводе задачи VS Code. Если приложение недоступно, команда показывает его имя и адрес и завершается ошибкой. Контейнеры остаются запущенными.

`npm test` требует запущенного стенда: запускает тесты стартовых ссылок, Vitest/React Testing Library, интеграционные тесты с PostgreSQL через Testcontainers и Playwright в Chromium. Smoke-проверки открывают кабинет и Аукцион, проверяют DSP по HTTP и готовность обеих БД.

`npm run down` останавливает стенд и сохраняет тома БД. `npm run typecheck` проверяет TypeScript обоих Next-приложений; `npm run test:go` запускает Go-тесты локально. После установки Go может понадобиться новое окно терминала для обновления PATH. Проверки вывода ссылок можно запустить отдельно командой `npm run test:startup`.

В кабинете доступны `/register`, `/login` и защищённый `/cabinet`. Локально можно открыть как `127.0.0.1`, так и `localhost` на настроенном порту. Рекламодатель регистрируется по email и паролю; администратор создаётся только операторской командой. Для создания администратора при работающем Docker-стенде выполните `npm run admin:create` и введите email и пароль интерактивно. Пароль не показывается. Обе роли входят через `/login`; сессия действует не более 24 часов от входа. На странице отображаются только собственные email и роль. Список пользователей, кампании, торги и статистика пока не реализованы.

Для просмотра логов используйте `docker compose logs -f cabinet` (или `auction`, `dsp`). В режиме `up` приложения работают из готовых Docker-образов: после изменения исходников повторите `npm run up` и обновите страницу в браузере.

## Разработка интерфейсов

Для правок интерфейса используйте Next Dev: `npm run dev:cabinet` для кабинета
или `npm run dev:auction` для Аукциона. Каждая команда поднимает DSP и две базы
в Docker, останавливает Docker-контейнер соответствующего фронтенда и запускает
Next локально на прежнем адресе. Если нужны оба интерфейса, запускайте команды
в двух терминалах. После сохранения исходника Next обновляет страницу без сборки
Docker-образа.

Режим разработки работает, пока его терминал открыт. Перед возвратом к полному
Docker-стенду остановите dev-процессы и выполните `npm run up`. База кабинета доступна локальному Next Dev через `127.0.0.1` и порт `CABINET_DB_PORT`; перед стартом применяется миграция. База DSP доступна только в сети Docker.
