# Тестовый аукцион

Проект тестового рекламного кабинета, DSP и Аукциона для проверки полного пути от настройки кампании до статистики. Сейчас согласованы архитектура, стек и тестовый подход; код приложений ещё не создан.

## Состав проекта

| Приложение | Назначение | Стек и данные |
| --- | --- | --- |
| Кабинет рекламодателя | Пользователи, кампании, креативы, ставки и просмотр статистики | Next.js + TypeScript, собственная PostgreSQL |
| DSP | Отбор кампании на bid request, события победы, показа и клика, расход и статистика | Go, собственная PostgreSQL |
| Тестовый Аукцион | Ручная отправка bid request, проверка порога и имитация событий | Next.js + TypeScript, без БД |

Для локального запуска согласован Docker Compose: три приложения и два отдельных контейнера PostgreSQL. Кабинет и DSP обмениваются данными через API и не читают таблицы друг друга.

## Сквозной сценарий

| Шаг | Наблюдаемый результат |
| --- | --- |
| 1. Рекламодатель входит в кабинет | Может создавать и менять только свои кампании; администратор видит всех пользователей и их кампании. |
| 2. Рекламодатель готовит кампанию | Указывает модель и сумму ставки, три таргета и один баннерный креатив 300×250 с изображением и обязательной ссылкой перехода. |
| 3. Рекламодатель включает кампанию | Кабинет сохраняет статус и передаёт актуальные настройки в DSP. Само включение bid request не создаёт. |
| 4. Пользователь вручную запускает запрос в Аукционе | DSP выбирает подходящую активную кампанию с максимальной сравнимой ставкой либо отвечает HTTP 204. |
| 5. Аукцион проверяет порог | При достаточной ставке сообщает DSP о победе и автоматически отправляет один показ; при 204 или ставке ниже порога событий победы и показа нет. |
| 6. Аукцион имитирует клик, если это включено | После показа инициирует один клик через DSP; DSP учитывает его и перенаправляет на ссылку креатива. |
| 7. Рекламодатель смотрит статистику | Видит участия, победы, показы, клики и расход только по своим кампаниям; администратор видит данные всех. |

## Работа с Git

- Для каждого эпика используется одна ветка `epic/<название-эпика>` без номера, например `epic/cabinet-access`.
- Каждая согласованная спецификация хранится в отдельной папке `specs/<имя>`. Сообщение коммита начинается с `feat:` для новой функции, `fix:` для исправления бага, `refactor:` для улучшения существующего кода или `chore:` для прочей работы. Для коммита по спецификации после префикса указываем точное имя её папки, например `feat: 001-registration`; отдельную нумерацию не добавляем. Для подготовительной работы без спеки указываем краткое название работы.
- Контрольные точки между спецификацией, планом и реализацией определяем для конкретной задачи; общий порядок ещё не утверждён.
- Перед завершением эпика проверяем всю ветку, запускаем необходимые тесты и при необходимости проводим рефакторинг.
- Pull request создаёт пользователь вручную; агент не создаёт PR.
- Ветка и коммит для подготовки каркаса согласовываются отдельно, поскольку это работа вне эпиков.
