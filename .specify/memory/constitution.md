# Конституция проекта «Тестовый аукцион»

## Core Principles

### I. Границы сервисов и владение данными

Кабинет рекламодателя, DSP и тестовый Аукцион MUST работать как три отдельных приложения.
Кабинет и DSP MUST иметь каждый свою PostgreSQL и владеть своей схемой данных.
Сервисы MUST обмениваться данными через описанные HTTP API; прямое чтение и изменение
таблиц другого сервиса запрещено. Аукцион в первой версии не хранит данные в собственной БД.
Разделение позволяет независимо проверять реальные границы между управлением кампаниями,
торгами и тестовым источником запросов.

### II. Требования и актуальная документация

Согласованные правила и критерии приёмки отдельной задачи MUST фиксироваться в её
Spec Kit spec.md. В docs/features/ MUST храниться документация действующей логики
функциональных областей: участники, сценарии, правила, состояния и ограничения.
После реализации или изменения поведения соответствующий документ MUST описывать
то, как функция работает сейчас. Историю «было/стало» и отдельные документы на каждую
задачу в docs/features/ вести нельзя. Корневой README.md и docs/Эпики.md MUST оставаться
согласованными с реализованной системой. Такое разделение даёт проверяемую постановку
задачи и понятное описание работающего продукта.

### III. Проверка через Red → Green → Refactor

Для каждого нового или изменённого проверяемого поведения MUST сначала быть написан
и запущен тест, который падает из-за отсутствующего или неверного поведения.
Затем MUST выполняться минимальная реализация до успешного теста; после полезного
рефакторинга затронутые тесты MUST запускаться повторно. Ошибка окружения или
установки не считается Red. Каждый критерий приёмки spec.md MUST иметь проверку,
а соответствие «критерий → тест» MUST проверяться перед завершением задачи.
Для изменений без проверяемого поведения MUST быть выбрана осмысленная проверка;
искусственный тест, повторяющий код, не требуется.

### IV. Права доступа и точный учёт

Права ролей admin и advertiser MUST проверяться на сервере; данные чужого
рекламодателя MUST быть недоступны через UI и API. Повторная доставка уведомления
о победе, показе или клике MUST не увеличивать счётчики и расход повторно.
Денежные единицы, точность представления и правила округления MUST быть определены
в спецификации соответствующей функции до реализации расчётов. Эти инварианты
защищают изоляцию пользователей и достоверность статистики.

### V. Воспроизводимая интеграционная проверка

Локальный полный сценарий MUST воспроизводиться через Docker Compose с тремя
приложениями и двумя отдельными контейнерами PostgreSQL. Правила Next.js-приложений
проверяются Vitest, интерактивные компоненты — React Testing Library; DSP — Go testing
и httptest. Работу с PostgreSQL MUST проверять интеграционными тестами с реальной БД
через Testcontainers для Node.js и Go. Межсервисные HTTP-контракты и полный путь
от запроса Аукциона до статистики в кабинете MUST иметь соответствующие проверки;
полный пользовательский путь проверяется Playwright против запущенных приложений.
В verification.md MUST записываться фактически выполненные проверки, их результат
и блокировки. Это позволяет обнаруживать ошибки на границах сервисов и честно
оценивать полноту результата.

## Дополнительные ограничения

- Кабинет и тестовый Аукцион — отдельные приложения Next.js на TypeScript,
  каждое со своим интерфейсом и серверным HTTP API. DSP — отдельный сервис Go.
- В первой версии Аукцион вручную отправляет bid request и имитирует результат.
  Автоматическая генерация запросов возможна позже, но не входит в текущий объём.
- Предметные правила и ещё не утверждённые детали определяются в spec.md
  соответствующей функции и согласованных проектных документах.
- У проекта один пользовательский README.md — в корне ad-platform/.
  Каталоги документации называются docs/ и docs/features/ строчными буквами.

## Рабочий процесс

Груминг определяет границы и проверяемые критерии задачи. После согласования
результат сохраняется в spec.md, затем готовятся необходимые артефакты Spec Kit:
уточнения, план, список задач и анализ согласованности. Реализация следует
Red → Green → Refactor. После изменения поведения обновляются документы в
docs/features/ и другие затронутые актуальные документы. Перед завершением
проверяются критерии приёмки, межсервисные границы, результаты тестов и
verification.md. Действия с Git, меняющие рабочую копию или историю, выполняются
только при отдельном разрешении, предусмотренном правилами рабочей области.

## Governance

Конституция обязательна для планов, спецификаций, задач, реализации и ревью.
Изменение принципов или обязательных ограничений требует согласования с
пользователем, обновления конституции и затронутых шаблонов и документов.
Версия изменяется по SemVer: MAJOR — несовместимая смена принципов или правил;
MINOR — новый принцип или существенное расширение требований; PATCH — уточнение
без изменения смысла. Дата принятия сохраняется, дата последнего изменения
обновляется при поправке. При планировании и перед завершением каждой задачи
агент MUST проверить соответствие конституции и объяснить необходимые исключения
до зависимой реализации.
