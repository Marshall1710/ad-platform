# Качество backend и данных

Применяйте к серверному коду кабинета и Аукциона, Go DSP и их PostgreSQL. Не вводите несогласованные правила торгов, денег или хранения; точность и округление задаются спецификацией соответствующей функции.

## API и границы

- Проверяйте входные данные на границе HTTP; различайте ошибку клиента, конфликт состояния и сбой сервера. Возвращайте устойчивые к повторному использованию контракты и понятные ошибки без утечки внутренних данных.
- Проверяйте роль и владельца ресурса на сервере на каждом пути чтения и изменения, включая списки, детали, статистику и переходы по идентификатору. Не принимайте владельца из запроса за доказательство права доступа.
- Явно задавайте таймауты, пределы размера входа и отмену работы при прекращении запроса там, где это влияет на доступность сервиса. В Go передавайте context через HTTP и операции с БД.
- Не пишите секреты, персональные данные и полные чувствительные payload в логи. Логируйте достаточно контекста для диагностики без скрытых побочных действий.

## PostgreSQL, деньги и события

- Каждая служба обращается только к собственной БД. Обмен между кабинетом и DSP идёт через описанный HTTP-контракт.
- Используйте параметризованные запросы и миграции, согласованные с текущей моделью данных. Индексы добавляйте под реальные запросы и подтверждённые ограничения уникальности.
- Для операций, которые должны изменить несколько записей вместе, выбирайте транзакцию. Повторная доставка события победы, показа или клика не должна увеличивать статистику и расход повторно; обеспечьте это устойчивым идентификатором события и ограничением/операцией в БД, когда такая логика реализуется.
- Ставки и расходы представляйте без ошибок двоичной арифметики с плавающей точкой. Конкретная денежная единица, масштаб, сравнение CPC/CPM и округление берутся из утверждённой спецификации.
- Не оптимизируйте запросы и не вводите кэш по предположению; сначала найдите медленный запрос или узкое место. При добавлении кэша определите актуализацию после изменения кампании.

## Проверка

- Разделяйте тесты чистых правил, HTTP-контрактов и работы с реальной БД. Для операций учёта проверяйте повтор, параллельное выполнение, отказ посередине и граничные денежные значения, когда эти случаи входят в поведение.
- Для Go используйте testing/httptest; для БД — реальный PostgreSQL через Testcontainers согласно конституции. Тест должен обнаруживать неверное поведение, а не повторять текущую реализацию.
